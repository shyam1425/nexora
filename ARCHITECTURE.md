# Architecture

## Layers

```text
App Router pages and client forms
        ↓
/api/v1 route handlers (auth, validation, CSRF, rate limits)
        ↓
Domain services (auth, recruitment, interview, offer, joining, documents)
        ↓
Prisma 7 client + MariaDB adapter
        ↓
MySQL 8
```

Server-rendered portal pages query Prisma directly for read-heavy dashboards. Mutations go through versioned REST handlers and domain services. UI components do not contain authorization or transaction rules.

## Runtime

- Next.js App Router with Node.js route handlers for database and storage operations.
- `next.config.ts` enables standalone output and security response headers.
- Prisma schema: `D:\project\prisma\schema.prisma`.
- Prisma CLI configuration: `D:\project\prisma.config.ts`; it loads `.env` and keeps the datasource URL out of the schema.
- Generated Prisma 7 TypeScript client: `D:\project\src\generated\prisma\` (regenerated by `npm run db:generate` and the build).
- `D:\project\src\lib\prisma.ts` owns the singleton and `PrismaMariaDb` adapter.
- Opaque, hashed session tokens are stored in MySQL; the raw token is never persisted.

## Domain boundaries

- `D:\project\src\lib\services\auth-service.ts`: account lifecycle, credential checks, verification, reset, sessions.
- `D:\project\src\lib\services\application-service.ts` and `application-state.ts`: candidate application creation and guarded state transitions.
- `D:\project\src\lib\services\job-service.ts`: job drafts and publishing.
- `D:\project\src\lib\services\requirement-service.ts`: client-owned requirements.
- `D:\project\src\lib\services\submission-service.ts` and `submission-review-service.ts`: recruiter submissions and client-owned review.
- `D:\project\src\lib\services\interview-service.ts`: interview scheduling and feedback completion.
- `D:\project\src\lib\services\offer-service.ts`: offer release, candidate response, and joining creation.
- `D:\project\src\lib\services\joining-service.ts`: employee activation after joining.
- `D:\project\src\lib\services\document-service.ts` and `document-access-service.ts`: private file lifecycle and authorization.
- `D:\project\src\lib\services\candidate-profile-service.ts`: candidate-owned profile updates, completion calculation, identity sync, and audit context.
- `D:\project\src\lib\storage\`: the storage adapter boundary. `types.ts` owns the canonical upload policy and key generation, `local-storage.ts` writes private files for single-instance deployments, and `s3-storage.ts` plus `s3-signing.ts` implement S3-compatible object storage with SigV4 signing. Services only ever see the `StorageAdapter` interface, so switching drivers never changes business logic.

## Data integrity

- Unique constraints prevent duplicate applications, submissions, client codes, job slugs, employee codes, and related records.
- Multi-step writes use Prisma transactions and conditional `updateMany` checks for concurrency.
- Application, submission, interview, offer, and joining changes create history/audit records and notifications where applicable.
- Notifications are created through a shared service; email delivery is isolated behind the email adapter.

## Current limitations

Local private storage is implemented for development and single-instance deployments with a persistent volume. S3-compatible object storage is implemented for horizontally scaled production deployments (`STORAGE_DRIVER=s3`, SigV4 signed, no AWS SDK dependency); it requires bucket credentials that are not available in this workspace, so live bucket verification is still pending. Payroll processing and advanced HR modules are outside the current MVP implementation.
